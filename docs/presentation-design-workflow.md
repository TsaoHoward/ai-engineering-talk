# 簡報內容與分鏡設計工作法 v0.1

> 專案：從寫 Code 到設計工作
>
> 目的：讓細綱能逐步轉成可檢查、可修改的敘事與畫面設計，而不是直接把細綱交給 AI 排版。
>
> 狀態：工作方法草案；可隨後續章節實際運用而修訂。
>
> 第一輪探索的**已確認結果、版本落差與下一輪邊界**，集中記錄於 [第一輪收斂紀錄](./design-round1-convergence.md)；本文件仍是候選方法，尚未升格為固定流程。

## 1. 核心順序

**細綱 → 章節責任 → 敘事 Beat → 案例／證據 → 低保真分鏡 → Slidev 實作與驗收**

每個階段解決不同問題；前一階段未穩定時，不要用後面的視覺或程式細節替它做決策。

- **細綱**：全場論點、章節安排、核心案例與預定轉場。
- **章節責任**：這章要解決什麼問題，哪些內容應留給後續章節。
- **Beat**：觀眾理解狀態的一次推進，不等於投影片或 Click。
- **案例／證據**：用具體、可信的材料讓觀眾看見差異及其意義。
- **低保真分鏡**：安排畫面焦點、閱讀順序、資訊揭露與前後連續性。
- **Slidev**：把已形成的分鏡實作成可以播放、講述、測試的畫面。

不要把「一個 Beat」「一張投影片」「一個 Click 狀態」視為同一單位。

## 2. 逐章工作流程

### Step 1｜章節責任

先對照 `outline/outline-v0.8.md`：

1. 本章回答什麼問題？
2. 觀眾進入前已經知道什麼？
3. 離開本章時應形成什麼理解？
4. 哪些概念只需要預告，不能在本章完整解答？
5. 轉入下一章的問題是什麼？

特別檢查跨章越界：例如第一章可以展示架構差異，卻應把 OOP／模組化設計原理與 System View → Work View 類比留給第二章。

### Step 2｜敘事 Beat

逐個 Beat 記錄四件事：

| 欄位 | 檢查問題 |
| --- | --- |
| Message | 此處只需要傳達哪一件事？ |
| Audience | 觀眾原本相信什麼，經過這一步後應理解什麼？ |
| Evidence | 什麼具體結果、畫面或例子能支持？ |
| Transition | 為何觀眾會自然需要下一步？ |

先討論資訊揭露的先後，不急著決定張數、版型或動畫。

### Step 3｜案例與證據檢查

選擇 Postman／API Client、Response JSON、Code Diff、檔案變更摘要、架構圖或 Prompt 等證據時，檢查：

- **合理性**：兩種實作可能都合理，不為了戲劇性編造低級錯誤。
- **因果性**：案例確實能支持 Beat 的結論，沒有跳過必要前提。
- **解釋成本**：目標觀眾能用很少背景理解差異。
- **一致性**：同一案例的 API 形狀、資料存取方式、命名和技術前提前後一致。
- **安全與授權**：優先使用合成／原創或允許重用的公開素材，不使用公司內部程式或資料。

尤其要區分：

1. **功能可用**：例如手動呼叫成功。
2. **與預期不同**：例如回傳資料的結構不一樣。
3. **違反專案契約**：例如前端依賴的資料路徑不相容。

只有在說明既有契約及依賴後，才能由第二點推進到第三點。

案例尚未定案時，明確標示待確認，不應讓細節探索持續阻礙整體敘事。

### Step 4｜低保真分鏡

每個畫面保留最少必要資訊：

| 欄位 | 意義 |
| --- | --- |
| 畫面任務 | 此畫面要讓觀眾注意到什麼？ |
| 主要視覺 | 以什麼具體證據或圖形為主角？ |
| 資訊層級 | 哪些內容是主、哪些只是輔助？ |
| 揭露順序 | 先看到什麼、後看到什麼？ |
| 口述與轉場 | 講者怎麼從這裡走到下一個畫面？ |
| 預估時間 | 是否符合章節時間預算？ |

優先沿用上一畫面的元素，讓觀眾感到正在深入檢查同一件事，而不是每頁重建脈絡。對技術案例，盡量重用跨章圖形；可以用 highlight、zoom、節點或連線變化表達視角轉換。

**一個畫面一個主要敘事任務**，但不必每個畫面都使用同一種雙欄、表格或卡片版型。

### Step 5｜Slidev 實作與驗收

分別驗收：

1. **內容正確性**：主張是否由證據支撐、是否與細綱相容？
2. **敘事節奏**：觀眾理解狀態是否自然推進、有無提前揭露答案？
3. **視覺品質**：焦點、閱讀順序、留白、字級、程式碼可讀性如何？
4. **播放與口述**：Click／動畫是否有意義，時間是否合理？
5. **技術品質**：Build、Playwright 視覺驗收、預覽是否通過？

技術驗收通過，不等於內容、敘事和視覺已通過。先以一段完整章節原型驗證做法，再擴展至全場。

## 3. 協作與變更規則

- **以章節管理內容，以 Beat 討論敘事，以畫面進行實作。**
- 每輪優先處理當前層次的決策；不要因為一個畫面細節而重寫整個故事。
- 紀錄**已確認、暫定、待確認**，不要將討論中的示意自動升格為定案規格。
- 當核心論點、章節安排或案例與 `outline/outline-v0.8.md` 產生實質差異時，先指出差異；決策確認後，再更新細綱版本，不要默默覆寫。
- 不必為每個 Beat 另建文件；只保存足以延續討論和交付 AI 實作的決策。
- 延後不必要的技術細節與視覺美化；避免過度程序化。

## 4. 第一章得到的具體經驗

- 先展示 Postman 手動呼叫成功等「功能可用」證據，再深入檢查，不要提前宣布 AI 做錯。
- 檢查順序由外而內：**Response 形狀 → 內部架構 → Naming**。三者不需要相同視覺權重。
- 同一組成果先看 AI 的實際作法，再揭露「如果由我來做，我預期怎樣」，最後追問預期從何而來。
- 在第一章將差異回收為「交辦內容與實際驗收依據的落差」；第二章才正式使用 OOP／模組化思維設計工作。
- 把可重用的架構圖保留給第二章，第一章展示差異，第二章解釋責任、介面與依賴。

## 5. 文件與實作的角色

- `outline/outline-v0.8.md`：當前內容與章節基準。
- `docs/presentation-design-workflow.md`：可重用的設計方法（本文）。
- `docs/storyboards/ch01.md` 等：逐章的敘事與低保真分鏡決策。
- `docs/slide-design-guidelines.md`：既有視覺指引；最終風格調整需另行確認。
- `slides.md` 與 `components/`：正式 Slidev 實作，不因整理本文件而改動。
