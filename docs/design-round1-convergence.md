## 3. 第一輪已確認的敘事決策

### 第一章：從交付落差認識規格

1. 同一支 `GET /api/orders`，先說明 AI 已完成指定查詢功能，**再由外而內檢查**：Response 形狀 → 架構分工 → Naming。
2. 「實作與我預期不同」不能直接等同「AI 做錯」。只有指出已存在的前端／共用 API／專案契約後，才討論交付不相容。
3. 收束在：交辦的是功能，實際驗收卻依賴未完整提供或確認的規格、邊界與背景；不是只需寫更長的 Prompt。
4. 第一章**不完整講授工作契約五要素，也不在此展開 OOP 類比**。

### 第二章：模組化原則轉用到工作

1. 從「這些就是工程師每天使用的規格」開始。規格可能分布在 API 文件、Method 簽章、Interface、Constructor、現有程式／測試；簽章不等於完整行為規格。
2. 借用具體 Controller → Service → DAO 合作，講責任、介面、依賴及封裝，不做 OOP 術語教學。
3. 以**抽出原則，再換設計對象**銜接：System View →「誰負責／怎麼合作／依賴什麼」→ Work View。
4. Work View 用 **建立 Table → 實作 API → 開發前端**，連線標示 Schema／API 契約。圖表現的是交接與依賴，**不是不可並行的固定時序**；更不代表節點一對一對映。
5. 沿用同一「實作 API」工作節點，聚焦並展開 Input、Output、Responsibility、Constraints、Acceptance。
6. 章末將細節收束為封裝：**對外承諾清楚，對內實作保有彈性**；會影響契約或驗收的未知事項仍須查證／協商。

### 第三章的切入點（尚未開始分鏡）

第二章封裝的是**一項工作的責任／介面**；第三章再討論把**一類工作中可重用的做法**抽出來：當次 Prompt → 區分共通與變動 → Skill。Skill 不等同 Class 或固定腳本。

### 資產界線

第一、二章與貫穿 Order API 的所有圖表、Code、畫面優先使用**合成／原創或確有重用權利的公開素材**；不使用內部專有程式或資料。這個方向與 v0.8「真實去識別化程式」的素材建議有差異，正式更新細綱時需同步註記。

## 6. 設計方法：暫時保留哪些、還要驗證哪些

繼續採用 **細綱 → 章節責任 → 敘事 Beat → 案例與證據 → 低保真分鏡 → Slidev 實作與驗收**，但此時仍稱為「候選工作法 v0.1」。

- **目前證實有用**：先界定章節責任／轉場；區分 Beat、頁面、Click；一個畫面一個主要敘事任務；重用視覺物件；維持「已確認／待確認」；以真正 Slidev 截圖而非 HTML 模擬檢查畫面。
- **還需整章試行**：分鏡何時足夠進入實作、案例核對需做到多細、章節連續口述與時間控制、哪些視覺規則值得共用、手機可讀性，以及 Fast Preview／Full QA 的最小合理配置。
- **不急著建置**：全場設計系統、複雜元件抽象、完整 CI 重構、更多孤立原型或第三章新的視覺技巧。

本階段的「完成」只表示**把探索結果整理成可查的決策和差異清單**；不表示第一、二章已完成。
