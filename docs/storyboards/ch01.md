# 第一章分鏡草案 v0.5｜問題從哪裡開始？

> 所屬簡報：從寫 Code 到設計工作
>
> 依據：[細綱 v0.8](../../outline/outline-v0.8.md) 的第一章 01–03
>
> 狀態：**敘事骨架基本確立；案例與低保真構圖仍屬草案；尚未實作 Slidev**
>
> 時間：**目標約 4 分鐘**。下列六個「畫面」是分鏡單位，不保證對應六張投影片。
>
> 素材：全部採原創、合成資料；不使用內部或機密專案素材。

## 1. 本章責任與邊界

### 本章要讓觀眾理解

**AI 可以完成指定功能；但「功能可用」不等於成果已滿足現有專案的交付要求。**

以同一支訂單查詢 API 為例：先建立功能驗證成功的印象，再由外而內檢查 Response 形狀、內部架構與 Naming，最後發現**交辦時提供的資訊**與**檢查成果時實際使用的判斷依據**不相同。

本章結束時應形成的問題是：**我究竟交出去的是一段功能描述，還是一項定義足夠清楚、能夠被委派與驗收的工作？**

### 本章不提前解答

- 不在第一章完整講解 OOP／模組化原理。
- 不在第一章展開 System View → Work View 類比。
- 不把 Input／Output／Responsibility／Constraints／Acceptance 當作本章已完整建立的工作模組模型。
- 不將解法簡化成「把 Prompt 寫更長」。

**第二章 04** 再用同一張架構圖，正式討論 Abstraction、Encapsulation、Interface、Responsibility、Dependency；**第二章 05** 才類比到工作模組。第一章可以預告需要「定義工作」，但不能代替第二章完成論證。

## 2. 固定的敘事順序

**交辦 → 功能驗證成功 → 實作比較（Response → 架構 → Naming）→ 回頭檢查交辦內容 → 提出工作定義問題。**

| Beat | 觀眾理解的推進 | 證據／主畫面 | 轉場 |
| --- | --- | --- | --- |
| 1 交辦 | AI 被要求完成一支 API | 原始需求 Prompt | 看它做出什麼 |
| 2 功能成功 | 產出確實可以使用 | API Client 200 OK、查詢結果；小型 Git 摘要 | 再仔細檢查成果 |
| 3 實作比較 | 功能相同，實作卻與我的預期不同 | Response → 架構 → Naming | 我的預期從哪裡來？ |
| 4 反思 | 我掌握的既有慣例沒有被完整交付／確認 | 原始交辦 vs 實際檢查依據 | 那工作應如何定義？ |
| 5 收束 | 需要的不只是補充一句 Prompt | 目前缺少的目標／邊界／規範／未決／驗收資訊 | 第二章：從模組設計找方法 |

注意：Beat 3 包含三層檢查，不代表需要三張同等權重的投影片。Naming 應從架構比較中順帶看見，而不是另外開一段講解。

## 3. 六個低保真畫面

| 畫面 | 任務與主要視覺 | 揭露／講述重點 | 時間暫估 |
| --- | --- | --- | --- |
| **01 交辦** | 只突出原始 Prompt：「新增訂單查詢 API，支援狀態、日期區間與分頁，回傳總筆數。」 | 保留足夠直觀的功能要求，不提前展示「正解」 | ~25 秒 |
| **02 成果可用** | 合成 API Client：GET /api/orders、HTTP 200、查詢結果。側邊可有小幅 Git 檔案變更摘要或 Swagger 片段 | 成功證據是主角；此時**不說它不對** | ~35 秒 |
| **03 Response 對比** | 延續 02 的 Response，放大後左右展開「AI 實作」與「我預期的」JSON 形狀 | 先見形狀差異，後揭露既有前端／API 契約；不要直接說它必然壞掉 | ~45 秒 |
| **04 架構對比** | 左右兩條合成實作路徑，從外部行為深入 Controller／Service／DAO／MyBatis／DB 等層次 | 強調「專案已經有既定實作路徑」，**不是**主張層數愈多愈好。Naming 輕帶 | ~45 秒 |
| **05 交辦 vs 驗收** | 左側原始需求，右側實際審查使用的判斷依據（Response 契約、架構、Naming） | 核心轉折：我當初有交代／確認這些嗎？ | ~40 秒 |
| **06 提出問題** | 原始功能描述旁，逐步浮現尚未界定的工作面向：目標、修改邊界、既有規範、未決事項、驗收 | 不完整給出工作契約模型；以「怎樣定義一項可委派的工作？」銜接第二章 | ~50 秒 |

合計約 **240 秒**，是排練前的暫估，不是正式口述時長。可用 Slidev Click 合併其中數個畫面，而不是固定做六張。

### 重要視覺轉場

- **02 → 03**：保留上一張的 Response，讓觀眾感覺是在放大檢查相同成果。
- **03 → 04**：比較方式保持連續，內容由外部 API 契約切入內部實作。
- **04 → 05**：收起技術細節，從「他做的不同」轉成「我憑什麼期待另一種做法」。
- **05 → 06 → 第二章**：由交辦缺口提出「如何設計工作」；第二章重用 04 的系統架構圖作為 System View 起點。

## 4. 合成案例：目前已決定與待確認

### 基本需求（暫定一致版本）

- 新增訂單查詢 API：狀態、日期區間、分頁、總筆數。
- Beat 2 用合成的 HTTP 200 與有資料的 Response 表示手動功能驗證成功。
- 「Postman 呼叫成功」只代表此路徑可用，不代表相容性、架構及全部測試已驗收。

### Response 形狀（選用方向，**未最終定案**）

候選 AI 實作（節錄）：

```json
{
  "data": [{ "id": "ORD-001" }],
  "totalCount": 42
}
```

候選預期實作（節錄）：

```json
{
  "data": {
    "items": [{ "id": "ORD-001" }],
    "totalCount": 42
  }
}
```

前提：既有前端或其他查詢 API 已約定從 `data.items` 與 `data.totalCount` 讀取分頁結果。此時差異是**既有整合契約**，而不只是個人喜好。上面只節錄 `data` 等欄位，不代表完整的共用 Response Wrapper。

**與 v0.8 細綱的差異**：原 01 是「AI 修改共用 `ApiResponse`，新增 `totalCount`」，預期方案是在 `data` 包 `items` 和 `totalCount`。目前採取的簡化對比沒有明示 AI 是否修改共用型別。實作前必須選定其中一種、確保其技術因果合理；若構成實質案例改動，再同步修訂細綱。**不要默默將兩種說法混用。**

### 內部架構（保留原細綱作為基準，**待實例驗證**）

原細綱設計為：

- AI：`Service` 直接使用 `JdbcTemplate`；
- 專案預期：`Controller → Service → DAO → MyBatis XML → Database`；
- Naming：如 `OrderRepository` vs `OrderDao`、`OrderResponse` vs `OrderQueryDto`。

前次討論曾用 `Controller → Repository → JDBC` 作圖形佔位，但那與 v0.8 的具體實作設定不同，**目前不視為新定案**。正式分鏡須選一個一致、可解釋的版本，避免 AI 路徑同時變換多項未交代前提。

這個比較不是在說 JDBC／Repository 天生錯誤，也不是在推崇過度分層；重點是**新功能要理解專案既有責任分工與依賴**。

### 未確認資訊與風險

- 完整 API Response 是否保留 `status`／`message` 等欄位，如何展示才能不誤解。
- API 行為與既有前端約定的最小證據，怎樣呈現而不增加解釋負擔。
- 架構示意需要多少具體 Code，是否足以銜接第二章 OOP 模組概念。
- 目前六畫面的字級、留白、播放與講述時間均未驗收。
- 原細綱「第一章以具體 Code 對比開場」已調整為「先顯示功能成功，再進入具體對比」，屬敘事順序調整；正式定案時應更新細綱說明。

## 5. 分鏡到實作的交付條件

目前**已確認**：

- 先功能驗證，再由外而內比較：Response → 架構 → Naming。
- 先呈現 AI 實際成果，再揭露自己的預期與預期來源。
- 第一章只提出工作定義問題；第二章才正式開始 System View → Work View 類比。
- 六畫面是低保真單位，不要求六張獨立投影片。

目前**尚未完成**：

- 對齊 API／架構合成案例與細綱的最終版本。
- 逐畫面口述、細節／證據與正式低保真 16:9 配置。
- Slidev 修改、動畫實作與視覺／播放驗收。
