## 1. 本章責任與邊界

### 本章要讓觀眾理解

**在同一個合成情境中，AI 版本呈現功能可用；但「功能可用」不等於成果已滿足既有專案的交付要求。**

以同一支訂單查詢 API 為例：先用明示為 Browser MSW 的實測 Mock HTTP 200 建立情境中的功能成功印象，再由外而內檢查 Response 形狀、內部架構與 Naming，最後發現**交辦時提供的資訊**與**檢查成果時實際使用的判斷依據**不相同。

本章結束時應形成的認識是：**我交辦的是功能，卻用既有專案的前提、邊界與契約來判斷能否交付。** 這些要求未必曾在交辦時明確提供，也未必確認 AI 已經掌握。下一章從此直接談起：**這些其實就是工程師每天依賴的各種「規格」。**

### 本章不提前解答

- 不在第一章完整講解 OOP／模組化原理。
- 不在第一章展開 System View → Work View 類比。
- 不把 Input／Output／Responsibility／Constraints／Acceptance 當作本章已完整建立的工作模組模型。
- 不將解法簡化成「把 Prompt 寫更長」。

**第二章 04** 應先承接「規格」：規格書、API 契約、程式型別、Method 簽章、Interface、Constructor、既有程式與文件，再從這些日常依據進到模組合作與封裝；**第二章 05** 才正式切換 System View → Work View。第一章不應提前完整給出工作模組或工作契約的答案。

## 2. 固定的敘事順序

**交辦 → 已驗證的 Browser MSW Mock 功能成功 → 實作比較（Response → 架構 → Naming）→ 回頭檢查交辦內容 → 發現交辦與驗收依賴的規格落差。**

| Beat | 觀眾理解的推進 | 證據／主畫面 | 轉場 |
| --- | --- | --- | --- |
| 1 交辦 | AI 被要求完成一支 API | 原始需求 Prompt | 看它做出什麼 |
| 2 功能成功 | 合成情境呈現 Chromium 已驗證的 Browser MSW 成功結果 | 標示 Browser MSW 的 API Client 200 OK、查詢結果及來源註記 | 再仔細檢查成果 |
| 3 實作比較 | 功能相同，實作卻與我的預期不同 | Response → 架構 → Naming | 我的預期從哪裡來？ |
| 4 反思 | 我掌握的既有慣例沒有被完整交付／確認 | 原始交辦 vs 實際檢查依據 | 這些判斷依據從哪裡來？ |
| 5 收束 | 我交辦的是功能，驗收卻依賴既有前提、邊界和契約 | 原始 Prompt 與既有 API／架構／命名約定對照 | 第二章：這些就是工程師每天使用的「規格」 |

注意：Beat 3 包含三層檢查，不代表需要三張同等權重的投影片。Naming 應從架構比較中順帶看見，而不是另外開一段講解。

### 重要視覺轉場

- **02 → 03**：保留上一張的 Response，讓觀眾感覺是在放大檢查相同成果。
- **03 → 04**：比較方式保持連續，內容由外部 API 契約切入內部實作。
- **04 → 05**：收起技術細節，從「他做的不同」轉成「我憑什麼期待另一種做法」。
- **05 → 06 → 第二章**：由「我沒交代／確認的要求」辨識「我其實仰賴的既有規格」，第二章直接用日常 Method／Interface／API 契約接住；不是立即切到 OOP 圖。待規格與模組合作的關係講清楚，再重用 04 的架構圖。

## 4. 合成案例：技術事實與證據邊界

本章唯一技術來源為 [TypeScript Synthetic Order API](../../examples/order-api/ts-v1/README.md)，證據對照見 [第一、二章 SSOT 對應](../ch01-ch02-ssot-alignment.md)。

### 需求與 HTTP 成功的意義

- 業務情境：新增 `GET /api/orders`，可依狀態、UTC 日期區間、`page`／`pageSize` 查詢，提供排序與篩選後 `totalCount`。
- 真正的瀏覽器演示 URL 為 `<site-base>/mock/api/{ai-direct|project-convention}/orders`，應清楚標註 **Browser MSW**。
- `src/application.ts` 的兩條實作均被 Chromium 測試透過 MSW API → 實際 Controller／Repository 或 Service／DAO／Drizzle → MSW DB Handler 呼叫；SQL 僅由受限 Mock Interpreter 對同一份 42 筆 Fixture 運算。
- 這可稱**瀏覽器 Mock API 的實測**，但不是部署真實 HTTP API Server 或 SQL Database，也不是特定 AI 模型實際產出的成果。

### Response → Consumer：不能只靠形狀就斷言壞掉

以 `pageSize=1` 的固定訂單資料為例，兩種版本實際回應形狀如下；正式投影片的完整值應直接從同版測試產物取得。

AI-direct：

```json
{"code":"OK","message":"success","data":[{"id":42,"customerId":1009,"status":"CANCELLED","createdAt":"2026-01-07T08:00:00.000Z"}],"totalCount":42}
```

Project-convention：

```json
{"code":"OK","message":"success","data":{"items":[{"id":42,"customerId":1009,"status":"CANCELLED","createdAt":"2026-01-07T08:00:00.000Z"}],"totalCount":42}}
```

`src/application.ts` 的 AI-direct 使用 `aiResponse()`；符合慣例的版本使用 `response()` 返回 `ApiResponse<T>` 外殼。**沒有實際修改同一個共用回應型別**；不得把「其他端點因修改共用型別遭破壞」說成既有程式的已驗證結果。

真正的不相容證據是 `src/existing-consumer.ts` 的 `readExistingOrdersConsumer` 依賴 `data.items`／`data.totalCount`，AI-direct 不符合、Project-convention 符合。額外 root 欄位本身不必然破壞一般 JSON Consumer。

### 架構與 Naming

- AI-direct：`createController → OrderRepository → parameterized SQL → DbTransport → MSW DB Handler`。
- Project-convention：`createController → OrderService → OrderDao → Drizzle ORM (sqlite-proxy) → DbTransport → MSW DB Handler`。
- 程式使用 `createController` 函式，並沒有另設 `OrderController` 類別。共用型別為 `OrderQuery`／`OrderPage`；不應再引用舊 Java DTO 與 MyBatis 名稱。
- Repository 與原生 SQL 不是錯誤；本章比較的是此合成專案既有 Consumer 契約、模組責任與交付方式。

### 待驗證的視覺與發布

- 開場 200 → Response → Consumer → 架構 → Naming 的連續揭露是否清楚而且低密度。
- `generated/browser-evidence.json` 是 CI Artifact，目前**尚未**自動匯入 Slidev，不能聲稱正式投影片已引用同版實測。
- 目前只完成本地靜態子路徑／Chromium 測試，**真實 GitHub Pages PR Preview** 的 MSW Worker Scope 尚未驗收。
- 本章約 4 分鐘及 Click／字級／16:9 的視覺檢查待工作包 B、C 實作。
