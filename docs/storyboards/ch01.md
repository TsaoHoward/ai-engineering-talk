## 1. 本章責任與邊界

### 本章要讓觀眾理解

**AI 可以完成指定功能；但「功能可用」不等於成果已滿足現有專案的交付要求。**

以同一支訂單查詢 API 為例：先建立功能驗證成功的印象，再由外而內檢查 Response 形狀、內部架構與 Naming，最後發現**交辦時提供的資訊**與**檢查成果時實際使用的判斷依據**不相同。

本章結束時應形成的認識是：**我交辦的是功能，卻用既有專案的前提、邊界與契約來判斷能否交付。** 這些要求未必曾在交辦時明確提供，也未必確認 AI 已經掌握。下一章從此直接談起：**這些其實就是工程師每天依賴的各種「規格」。**

### 本章不提前解答

- 不在第一章完整講解 OOP／模組化原理。
- 不在第一章展開 System View → Work View 類比。
- 不把 Input／Output／Responsibility／Constraints／Acceptance 當作本章已完整建立的工作模組模型。
- 不將解法簡化成「把 Prompt 寫更長」。

**第二章 04** 應先承接「規格」：規格書、API 契約、程式型別、Method 簽章、Interface、Constructor、既有程式與文件，再從這些日常依據進到模組合作與封裝；**第二章 05** 才正式切換 System View → Work View。第一章不應提前完整給出工作模組或工作契約的答案。

## 2. 固定的敘事順序

**交辦 → 功能驗證成功 → 實作比較（Response → 架構 → Naming）→ 回頭檢查交辦內容 → 發現交辦與驗收依賴的規格落差。**

| Beat | 觀眾理解的推進 | 證據／主畫面 | 轉場 |
| --- | --- | --- | --- |
| 1 交辦 | AI 被要求完成一支 API | 原始需求 Prompt | 看它做出什麼 |
| 2 功能成功 | 產出確實可以使用 | API Client 200 OK、查詢結果；小型 Git 摘要 | 再仔細檢查成果 |
| 3 實作比較 | 功能相同，實作卻與我的預期不同 | Response → 架構 → Naming | 我的預期從哪裡來？ |
| 4 反思 | 我掌握的既有慣例沒有被完整交付／確認 | 原始交辦 vs 實際檢查依據 | 這些判斷依據從哪裡來？ |
| 5 收束 | 我交辦的是功能，驗收卻依賴既有前提、邊界和契約 | 原始 Prompt 與既有 API／架構／命名約定對照 | 第二章：這些就是工程師每天使用的「規格」 |

注意：Beat 3 包含三層檢查，不代表需要三張同等權重的投影片。Naming 應從架構比較中順帶看見，而不是另外開一段講解。

## 3. 六個低保真畫面

| 畫面 | 任務與主要視覺 | 揭露／講述重點 | 時間暫估 |
| --- | --- | --- | --- |
| **01 交辦** | 只突出原始 Prompt：「新增訂單查詢 API，支援狀態、日期區間與分頁，回傳總筆數。」 | 保留足夠直觀的功能要求，不提前展示「正解」 | ~25 秒 |

| **05 交辦 vs 驗收** | 左側原始需求，右側實際審查使用的判斷依據（Response 契約、架構、Naming） | 核心轉折：我當初有交代／確認這些嗎？ | ~40 秒 |
| **06 收束規格落差** | 原始功能要求和剛才用來檢查的既有 Response 契約、架構分工、命名規則同時留在畫面 | 不是再多列一套工作契約欄位，而是指出：工程師原本靠這些既有規格工作；如果不了解背景就盲寫，人類工程師也未必有更好的結果 | ~50 秒 |

合計約 **240 秒**，是排練前的暫估，不是正式口述時長。可用 Slidev Click 合併其中數個畫面，而不是固定做六張。

### 重要視覺轉場

- **02 → 03**：保留上一張的 Response，讓觀眾感覺是在放大檢查相同成果。
- **03 → 04**：比較方式保持連續，內容由外部 API 契約切入內部實作。
- **04 → 05**：收起技術細節，從「他做的不同」轉成「我憑什麼期待另一種做法」。
- **05 → 06 → 第二章**：由「我沒交代／確認的要求」辨識「我其實仰賴的既有規格」，第二章直接用日常 Method／Interface／API 契約接住；不是立即切到 OOP 圖。待規格與模組合作的關係講清楚，再重用 04 的架構圖。

## 4. 合成案例：目前已決定與待確認

### 基本需求（暫定一致版本）

- 新增訂單查詢 API：狀態、日期區間、分頁、總筆數。
- Beat 2 用**標示為合成／模擬**的 HTTP 200 與 Response 示意情境中的功能可用；不代表已實際執行 Java API。
- 「API Client 顯示 HTTP 200」在此是**情境示意**，不是既有合成 Java 程式實際執行／測試的證據；也不能推論相容性、架構或整體驗收已通過。

### Response 契約（技術設定已固定，視覺截取方式仍可調整）

以既有 [合成案例](../../examples/order-api/README.md) 的兩份實作為準，**不再以只剩 `data` 的簡化 JSON 當作獨立技術版本**。

AI 直接實作的端點回應（示意）：

```json
{
  "code": "OK",
  "message": "success",
  "data": [{ "id": 1 }],
  "totalCount": 42
}
```

符合既有專案慣例的回應（示意）：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "items": [{ "id": 1 }],
    "totalCount": 42
  }
}
```

**技術因果：**原共用外殼固定 `{ code, message, data }`。AI 為單一端點修改共用 `ApiResponse<T>`，增加 root `totalCount`；若序列化包含 null，其他端點的回應也可能多出 `totalCount: null`。預期方案保留共用外殼，將分頁資訊放進 `data`。不是說 root `totalCount` 一律錯，而是**與此合成專案已存在的契約不符**。

正式畫面可以局部放大 `data`／`totalCount`，但需透過標籤或口述明示共用型別被修改的因果；範例中的 `id` 和 `42` 是合成展示值。

### 內部架構（技術設定已固定）

以 `examples/order-api/ai-direct.md` 與 `project-convention.md` 為唯一技術基準：

- AI：`OrderController → OrderRepository → NamedParameterJdbcTemplate → Database`（沒有沿用既定 Service／DAO／MyBatis XML 分層）。
- 既有慣例：`OrderController → OrderService → OrderDao → MyBatis XML → Database`。
- Naming：`OrderRepository`、`OrderResponse` vs `OrderDao`、`OrderQueryDto`／`OrderPageDto`。
- 分頁參數名稱採用合成程式的 `page`、`pageSize`，不混用 `size`。

上述設定與 v0.8 細綱的「Service 直接使用 JdbcTemplate」不同，已在 [v0.9 候選](../../outline/outline-v0.9-candidate.md) 對齊。

這個比較**不表示 JdbcTemplate／Repository 技術上不合理**，也不是推崇層數越多越好；重點是成果沒有沿用這個合成專案已建立的模組分工與契約。

### 未確認資訊與風險

- 已固定共用 Response 外殼為 `{ code, message, data }`；仍需驗證舞台上的截取／放大方式能否清楚傳達「更動共用契約」的因果。
- API 行為與既有前端約定的最小證據，怎樣呈現而不增加解釋負擔。
- 架構示意需要多少具體 Code，是否足以銜接第二章 OOP 模組概念。
- 目前六畫面的字級、留白、播放與講述時間均未驗收。
- 已在 `outline-v0.9-candidate.md` 反映「先交辦＋合成成功情境，再做具體對比」；尚待跨章連續播放驗收後才升格為全場基準。

## 5. 分鏡到實作的交付條件

目前**已確認**：

- 先功能驗證，再由外而內比較：Response → 架構 → Naming。
- 先呈現 AI 實際成果，再揭露自己的預期與預期來源。
- 第一章收在「交辦內容與既有規格的落差」；第二章先談工程師日常依賴的規格，再建立 System View → Work View 類比。
- 六畫面是低保真單位，不要求六張獨立投影片。

目前**尚未完成**：

- 已形成 v0.9 候選技術設定；仍需完成**Slidev 中的呈現對齊**與合成情境的來源標示。
- 逐畫面口述、細節／證據與正式低保真 16:9 配置。
- Slidev 修改、動畫實作與視覺／播放驗收。
