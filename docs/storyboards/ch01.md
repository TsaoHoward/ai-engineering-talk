# 第一章分鏡草案｜問題從哪裡開始？

> 對齊 [v0.9.3 候選細綱](../../outline/outline-v0.9-candidate.md)
>
> 目標：約 4 分鐘；以下六個畫面是分鏡單位，實際投影片與 Click 數待視覺原型決定。

## 本章要表達什麼？

**程式能執行，仍可能忽略既有專案的隱含契約。**

同一支訂單查詢 API：先看到功能成功，再檢查錯誤回應的 `message`。專案原本要求 `message` 存代碼（如 `m0001`），前端透過代碼表顯示對應訊息；AI-direct 卻直接填入錯誤文字。最後回到交辦內容，發現原本依賴的既有規格沒有被明確交付。

## 六個低保真畫面

| 畫面 | 主要視覺 | 觀看與講述重點 | 暫估 |
| --- | --- | --- | --- |
| 01 交辦 | 一份簡短的新增訂單查詢 API Prompt | 觀眾先理解功能要求 | 25 秒 |

## 連續觀看的重點

- **02 → 03**：從正常查詢切換到同一支 API 的錯誤處理，避免把 HTTP 200 與錯誤代碼當成同一個回應。
- **03**：先看到 `message` 值不同，再展示前端為何需要代碼。設計焦點是「欄位約定」，不再比較 `items`／`totalCount` 的位置。
- **03 → 04**：由對外契約擴展至內部分工，保留相似的比較語言。
- **04 → 05 → 06**：收起技術細節，回看交辦與隱含規格的落差；第二章接著說明規格如何支援模組合作。

## 素材來源與待辦

- **已存在**：TypeScript 兩種分層實作、合成訂單資料、Browser MSW 正常查詢與測試。
- **待對齊**：合成 API 的錯誤回應 `message`、前端代碼表與相容性測試；目前 Repository 的 `message` 尚未實作本分鏡的錯誤碼契約。
- **待設計**：03 的錯誤回應／代碼表如何呈現，以及整章 16:9 字級、視覺密度、揭露順序。
- **證據原則**：使用同一版本程式及測試產出的展示資料。未對齊前的 `m0001` 僅是細綱要求的示意代碼。

本文件保存內容與觀看順序；視覺原型決定具體版面和 Click。
