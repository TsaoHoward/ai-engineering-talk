## 1. 本章責任與跨章銜接

### 從第一章直接接住的問題

第一章不是停在「AI 要看更多 Prompt」，而是發現：

**我交辦的是功能，但我判斷成果是否可交付時，依賴了既有系統的前提、邊界與契約。**

第二章的第一句應接近：

> 其實這些東西，就是我們工程師每天都在使用的「規格」。

規格不只是一份完整的規格書；它可能體現在 API 文件、專案文件、程式註解、Method 簽章、型別、Interface、Constructor、既有程式或測試之中。並非每一項資訊都有相同的保證力：**簽章描述部分輸入與輸出，完整的行為仍可能需要其他契約或查證。**

如果人類工程師同樣沒看過相關規格、直接盲寫，結果也未必比 AI 更符合專案需求。因此這是**軟體工程既有的協作問題**，不只是 AI 特有問題。

### 本章要建立的認識

1. 工程師在有限資訊下，靠規格、介面與既有設計合作。
2. 模組化設計讓我們管理責任、對外介面、依賴及內部細節。
3. 相同的設計思維能轉用於**工作單元之間的交接與合作**，而非 Class 與 Skill 的一對一對應。
4. 對外契約要足夠明確，執行者不需要事先規劃好所有內部細節；真正影響契約的未知事項仍須查證或協商。

### 本章不提前處理

- 不把第二章變成 OOP 語法或設計模式教學。
- 不用「五個名詞、五個定義」取代具體合作案例。
- 不在此介紹 Skill 的技術格式或完整工作流。
- 不把「建 Table → 做 API → 做前端」當作固定、不可並行的開發流程；真正要展示的是工作間的交付與依賴。Work View 將在後續 SDLC／Workflow 章節繼續擴充。

## 3. 核心視覺與揭露順序

### A｜規格存在於日常開發的很多地方（Beat 06）

畫面從第一章的 API 契約延伸，而不是突然跳到一張 OOP 架構圖。

可以從**唯一合成案例的 `OrderService`** 真正的方法簽章開始；來源為 [`src/application.ts`](../../examples/order-api/ts-v1/src/application.ts)，不是為投影片另造的 Interface：

```ts
async search(query: OrderQuery): Promise<OrderPage>
```

由觀眾已熟悉的具體問題引出其他規格形式：

- 新作 Method：要接收什麼、回傳什麼？
- 呼叫既有 Method：怎麼使用、預期行為是什麼？
- 實作 Interface：需要實作哪些方法？
- 建構物件：Constructor 依賴什麼？
- 增加 API：Request／Response 與前端如何約定？
- 加入既有專案：專案文件、既有程式、測試裡有哪些慣例？

**揭露方式：**先讓觀眾認出一個日常 Method，再逐步拉遠，發現規格分散在不同載體，而非在一張畫面同時塞滿六個例子。

**必要口述：**Method 簽章不等於完整業務規格；只是工程師已習慣在有限資訊和既有約束中工作。若沒查這些資料直接寫，人類也會犯相似錯誤。

同頁可揭露 [`OrderQuery`／`OrderPage`](../../examples/order-api/ts-v1/src/domain.ts)、`OrderDao` 的建構子依賴、[`ApiResponse<T>` 與既有 Consumer](../../examples/order-api/ts-v1/src/existing-consumer.ts)。它們是不同強度的規格證據；不得僅從 Method 型別推論完整 UTC／排序與分頁規則。

### B｜模組為什麼能在有限資訊下合作？（Beat 07）

第一章展示過的架構圖在此重用：

```text
createController → OrderService → OrderDao → Drizzle (sqlite-proxy) → DbTransport → MSW DB Handler
```

不再拿來證明 AI 路徑不同，而是逐次聚焦：

1. **Responsibility**：Controller 函式、Service、DAO 分別負責什麼？
2. **Interface**：相互使用時，約定哪些呼叫方式、資料與行為？
3. **Dependency**：誰依賴誰、有哪些既有條件？
4. **Encapsulation**：在契約成立的情況下，呼叫端不必知道內部實作的全部細節。

**Abstraction** 是抽出責任與介面的設計思維，穿插於上述例子，不必另開一頁作孤立定義。

**論述限制：**這個模組分層是本案例採用的合理設計，不主張層數越多越好，也不表示介面不需查證。

### C｜同一個目標，兩種設計視角（Beat 08）

畫面應明確切換「在看什麼」，而非將每一個節點一對一重新命名。

```text
System View（交付的系統）
createController → OrderService → OrderDao → Drizzle → MSW DB Handler

Work View（完成系統的工作）
建立 Table → 實作 API → 開發前端
```

- **System View**：模組在執行時如何合作、彼此依賴哪些介面。
- **Work View**：工作單元間交付什麼成果、下游需要哪些前提、誰負責整合。
- Work View 可先用箭頭表達直覺的交接／依賴，但**不是固定時間順序**：API 契約可以事先討論、前端可用 Mock 進行開發；相關非線性關係留到 SDLC／Workflow 章節再展開。

**已確認的視覺方案：以「抽出模組設計原則，再應用到工作」為敘事邏輯，但用同一組連續圖形呈現，不額外插入一張理論課式的定義表。**

三個連續狀態（可用同頁 Click 或相鄰投影片實作，尚不固定頁數）：

1. **狀態 1｜System View：模組如何合作？** 保留上一段已看過的 `createController → OrderService → OrderDao`，簡短回收責任、介面、依賴，不重新講授 OOP 名詞。
2. **狀態 2｜抽出共同設計問題**：原圖逐步弱化，只保留「誰負責？」「怎麼合作？」「依賴什麼？」；講述「剛才設計的是交付後的系統；如果改看完成它的工作呢？」。此狀態應短促，可是一個 Click，不必獨立一張投影片。
3. **狀態 3｜Work View：工作如何交接？** 改為 `建立 Table → 實作 API → 開發前端`，仍使用節點、箭頭、聚焦等視覺語言。**箭頭上標明交接物**：Table／API 之間為 Schema／資料規則；API／前端之間為 API 契約。不要做 Controller 與建立 Table 等節點之間的一對一 Morph，避免暗示等價。

**下一個聚焦動作**：保留 Work View 的上下游位置，突出中間「實作 API」；然後放大這個工作單元，顯示它的工作契約：

| 面向 | 此案例的內容 |
| --- | --- |
| Input | 訂單查詢需求、DB 結構／相關文件、既有 API 與專案規範 |
| Output | 可整合的 API 程式變更、必要測試、交付說明 |
| Responsibility | 完成指定訂單查詢功能 |
| Constraints | 遵守既有分層、命名、Response 契約與修改邊界 |
| Acceptance | 功能、整合契約與測試證據符合要求 |

**核心類比：**不是「Controller = 建立 Table」或「Service = 實作 API」，而是兩種視角都需要處理責任、合作介面與依賴。

**合成案例與 Work View 的界線：**「建立 Table」是一般軟體開發工作示意；這份 Browser MSW 演示只有唯一的 Drizzle `schema.ts`、固定 Fixture 與受限 SQL Mock，沒有部署／建立真正的 DB Table。應用 “設計 Schema／建立 Table” 作工作節點時，需明示概念性質，避免把 Mock 視為真實資料庫運作。

這張 Work View 應保留為後續工作流程、上游下游交接及 SDLC 圖形的底圖。

### D｜回扣「封裝」（Beat 09）

在前一段 Work View 的「實作 API」上放大，做同結構但非同一技術物件的對照：

| | 程式模組 | 工作單元 |
| --- | --- | --- |
| **對外要清楚** | 方法／介面、行為承諾、依賴條件 | 目標、輸入輸出、邊界、限制、驗收 |
| **內部可封裝** | 實作細節、演算法或實現策略 | 調查方式、執行步驟、工具與實作選擇 |
| **不能忽略** | 破壞介面或既有行為的變更 | 影響交付契約的未知事項與風險 |

這時才回答「難道把工作交出去前，所有東西都要先規劃好？」——**不用**。好的封裝不是預知內部每一步，而是讓外部可以依靠契約合作，同時保留執行者處理細節的空間。

需避免兩種誤解：

- 內部可自主處理 ≠ 可以忽略已存在的契約。
- 未知事項可以存在 ≠ 影響介面／驗收的未知事項可以不告知、不確認。

## 4. 與第三章的轉場：封裝的另一個層次

第二章尾聲：

> 我們可以定義一項工作的對外契約，讓執行者在約定的邊界內自行完成工作。

接著第三章才問：

> 那麼，要怎麼把這些工作要求交給 AI？如果每次執行 API 開發都有相似的規範、檢查方法和工作程序，是否可以把**可重用的做法**再封裝起來？

第三章保留細綱的原有順序：

1. **Prompt**：把這次工作的契約交給 AI，或提供讓 AI 能查到契約的資料。
2. **區分變動與共通**：每次 API 的需求不同，但確認既有規格、實作、測試、回報的部分方法可以重用。
3. **Skill**：封裝一類工作的程序、指引、資源及檢查方式。

不要將「封裝工作責任」與「封裝可重用執行方法」混為一談；Skill 也不等同 Class 或完全固定的腳本。

## 5. 時間與視覺待決事項

本章暫定 5 分鐘，可以用約 4–6 個畫面／多個 Click 來呈現；不應被細綱的兩個內容單元限制張數。現階段尚不固定畫面數量。

**已確認：**

- 第二章從「工程師每天依賴的規格」接第一章，而非直接切回 OOP。
- 用 Method、Interface 等真實開發場景說明規格，再解釋模組合作。
- System View → Work View 的代表案例：**建立 Table → 實作 API → 開發前端**。
- System View → 三個共同設計問題 → Work View 的三狀態分鏡已決定；先看工作間合作，再放大「實作 API」的工作契約。
- 「不用預先規劃所有細節」放在章末扣回 **Encapsulation**，並開啟第三章 Skill。

**尚待視覺設計階段確認：**

- Beat 06 直接使用 `OrderService.search(query: OrderQuery): Promise<OrderPage>`；是否增加 API Spec／Constructor 第二層視覺，留待整章 16:9 分鏡驗收。
- 三狀態已確立，但要以同頁 Click、跨頁連續畫面或其他方式實作，仍待 16:9 原型驗證。
- Work View 箭頭已決定標註 Schema／API 契約；字級和箭頭呈現如何清楚傳達依賴而非固定時間順序，仍待原型驗證。
