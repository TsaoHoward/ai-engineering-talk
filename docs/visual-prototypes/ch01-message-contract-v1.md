# 第一章｜`message` 契約視覺原型 v1

> **性質**：單頁 HTML／三個連續觀看狀態，僅用於檢驗資訊層級與觀看節奏
>
> **來源**：[現行第一章分鏡](../docs/storyboards/ch01.md)、[Order API 案例契約](../docs/order-api-case-scope.md)、案例 PR #13
>
> **檔案**：[`prototypes/ch01-message-contract-v1.html`](../prototypes/ch01-message-contract-v1.html)

## 這次設計的範圍

只處理第一章分鏡的「02 功能可用 → 03 訊息契約」，拆成三個連續觀看狀態：

| 狀態 | 畫面主角 | 觀眾應理解 |
| --- | --- | --- |
| 1 成功查詢 | `GET`、HTTP 200、三筆訂單、42 筆總數 | 先建立功能完成的印象 |
| 2 錯誤比較 | 同一種 HTTP 400，`message` 為原文或 `m0001` | 看見兩種結果不一致 |
| 3 揭露契約 | 既有 Consumer 的訊息表 `m0001 → 查詢條件不合法` | 了解為什麼第二種可整合 |

狀態 1 為正常請求；狀態 2、3 切到無效日期 `2026-02-30` 的錯誤請求。兩者不混在一個 HTTP 回應。

## 畫面設計決策

- 每個狀態只有一個主標題，保留充足留白。
- 成功畫面以 HTTP 狀態與訂單結果建立上下文；不提前揭露錯誤。
- 錯誤比較保留雙欄固定位置，顯著突顯 `message` 一欄。
- 第三個狀態用同一組訊息值接上前端查表，讓觀眾從「不同」推進至「無法整合」。
- 目前先使用單一藍色聚焦色、白底及中性色，暫不建立全場 Design System。
- HTML 可用畫面下方按鈕或鍵盤左右箭頭切換；一個畫面狀態不強制對應一張正式投影片。

## 技術與素材對照

- `#42 / #35 / #28` 的顯示內容來自 `fixtures/orders.json` 的固定資料；42 筆總數與 `pageSize=3` 來自案例測試。
- `INVALID_QUERY`、`invalid UTC date interval`、`m0001`、代碼解釋來自 `src/application.ts`、`src/message-catalog.ts` 與 Browser E2E。
- 本原型是**靜態視覺草模**：它呈現同版程式已證明的案例事實，但不執行 Browser MSW。正式簡報整合應改從單一程式／測試來源引用資料。
- 正式投影片及 `slides.md` 保持不變。

## 已執行的低保真檢查

- Chromium 1600 × 900 比例下，三個狀態均可獨立擷取；實際截圖 1600 × 901（邊界四捨五入）。
- 三個狀態的主要排版沒有垂直內容溢出。
- 按鈕與鍵盤左右箭頭可以正確切換狀態。
- 程式／測試來源已核對；**尚未**做講述排練或實際投影驗收。
